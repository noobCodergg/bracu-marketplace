# Free-tier production scaling implementation

## Target

- 200 people browsing the web app at the same time.
- A burst of 100 distinct visitors requesting the same public catalog API.
- Overload must return controlled `429` or `503` responses instead of exhausting the Node process or MongoDB connection pool.

This is a design target, not a capacity guarantee. Final capacity must be measured against the deployed Render service and production-like Atlas data.

## Implemented in code

- Global admission control: 40 active API requests, 160 queued requests, 5-second queue timeout.
- Per-identity endpoint rate limit: 20 requests/second; authentication 5/second; analytics ingestion 2/second.
- Shared-network protection: 200 requests/second per public IP while `X-Visitor-Id` separates legitimate users behind the same campus NAT.
- MongoDB pool capped at 10 connections with idle cleanup and a 5-second server-selection timeout.
- Public product responses cached in-process with a 200-entry bound and request coalescing. One hundred identical cold-cache requests execute one handler.
- Public responses advertise CDN caching with `s-maxage`, stale-while-revalidate, and stale-if-error. Private and mutating API traffic is `no-store`.
- Product search uses MongoDB's text index and catalog queries have a 3-second database execution ceiling.
- Browse analytics were removed from catalog GET handlers and moved to a bounded batch endpoint, deduplicated per visitor/product/10-minute bucket.
- Expensive seller/admin analytics have smaller isolated concurrency bulkheads.
- Production does not expose the internal load-test route.
- System Analytics reports live concurrency, queue depth, shed requests, endpoint latency/errors, database health, and suspicious actors.
- `.github/workflows/keep-render-warm.yml` calls the public health endpoint every five minutes.

## Required deployment settings

Set these Render environment variables:

```text
NODE_ENV=production
DB_MAX_POOL_SIZE=10
API_MAX_IN_FLIGHT=40
API_MAX_QUEUE=160
API_QUEUE_TIMEOUT_MS=5000
AUTH_CACHE_TTL_MS=30000
TRUST_PROXY_HOPS=1
ENABLE_REQUEST_DB_TELEMETRY=false
```

Also set unique production values for `JWT_SECRET`, `MONGODB_URI`, `CLIENT_URL`, and the admin bootstrap values. Never copy development secrets into production.

## GitHub keep-warm setup

In GitHub, open **Settings → Secrets and variables → Actions**, create repository secret `RENDER_HEALTH_URL`, and set it to:

```text
https://YOUR-RENDER-SERVICE.onrender.com/api/v1/health
```

Run **Keep Render API warm** once with `workflow_dispatch`, then confirm a green run. Scheduled Actions can be delayed, and Render/GitHub free tiers do not provide an uptime guarantee.

## Cloudflare setup

1. Proxy the frontend/custom domain through Cloudflare (orange cloud).
2. Cache immutable frontend assets for a long browser/edge TTL. Filenames generated by Vite are content-hashed.
3. For the API hostname, add a Cache Rule only for `GET /api/v1/products*`. Respect origin cache-control headers.
4. Bypass cache when a `Cookie` or `Authorization` header is present.
5. Always bypass `/auth`, `/account`, `/orders`, `/admin`, `/seller`, `/notifications`, `/reports`, `/analytics`, and every non-GET request.
6. Do not cache error responses or personalized data. Purge the product API cache after a deployment if catalog response shape changes.

## Release gate

Before public launch, run a load test against the deployed public product endpoint using 100 virtual users and unique `X-Visitor-Id` values. Test a warm-cache burst and a cold-cache burst. Pass criteria:

- no transport errors or process restart;
- warm public catalog P95 under 500 ms;
- error rate below 1% under the agreed traffic model;
- MongoDB pool does not saturate;
- memory remains stable for 15 minutes after the test;
- intentional excess load returns `429`/`503` with `Retry-After`.

Do not load-test login with GET: login is a POST endpoint and is intentionally limited to protect accounts.

## Capacity decision

The code now safely bounds work and is structured for the 100-request identical-public-API burst. It cannot honestly guarantee that every arbitrary database-writing API will complete 100 simultaneous requests on a free Render/Atlas tier. Orders, authentication, and analytics are deliberately rate-limited or queued. Promote the target only after the deployed release gate passes; otherwise reduce active concurrency or move the database/backend to a paid tier.
